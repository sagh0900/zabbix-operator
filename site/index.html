Attention

In 2017, Attention Is All You Need turned intelligence into something you can commoditize. Models now help improve their own successors, and the time between releases keeps shrinking. Machines are getting very good at paying attention.

So I keep asking myself: how much attention do we pay, inward and outward? To our work, to the people it touches, to what is actually true? Or do we keep rolling on borrowed beliefs, assumptions and biases, limited by what we think we know, which often has nothing to do with reality?

The incident

In late 2025 I caused a Zabbix incident. Proxies were timing out against the server, and I added session affinity to the Zabbix Kubernetes Service to fix it. It did the opposite: it pushed the proxies into backoff.

A lot of people were pulled in, most with no idea where it came from, and it took a long time to trace it back to the change and to me. I reverted it, and I had to answer for something I never intended.

I took it personally. Not as blame, but as a question: how do I solve this next time without putting myself in the same spot again?

What was really wrong

Session affinity was a patch on a problem nobody had named. Zabbix runs in native HA: one server node is active and accepts connections; the others wait as standbys and do not listen at all. The Service in front of them selected every server pod, so a share of every new proxy and agent connection landed on a node that would never answer.

The fix is not a setting on the Service. It is making the active node explicit, the way CloudNativePG makes the primary explicit.

Building it, and moving the database

So I built an operator, with AI-assisted coding, and ran it in test. One blocker remained: production Zabbix still ran on an external Patroni PostgreSQL cluster, and the operator builds on a CloudNativePG-managed one.

One Friday morning I decided that the day had come. An earlier attempt at logical replication had already failed; it failed for me too, ate time, and the weekend was coming. So I switched to physical replication.

  • 40 minPhysical copy of 500 GB into a CloudNativePG replica.
  • 30 minWAL replay to catch up: a standby in about 1 hour 10 minutes.
  • 40 minA full backup to S3 before touching anything.
  • minutesThe cutover, agreed beforehand with the team that would feel it.
  • afterAnother full backup; daily scheduled backups and continuous WAL archiving for point-in-time recovery since.

Everything was ready by the end of the day, but the cutover was the part that scared me. I did not want a second incident. So before switching, I went to the person whose team relies on Zabbix every day, told them what I was doing and that Zabbix would be down for a few minutes, and we agreed on it together. The switch took a few minutes, and it worked.

What I would defend

My instinct comes from CI/CD: prove it in lower environments, roll it out, and tell the people who use it about the brief disruption instead of waiting for a window. I did not take this one through the formal change process, and that is not the part I would defend.

The conversation is. Telling the person who would feel it is what made this a change, and not a repeat of the incident.

Attention, it turns out, is also something you pay to other people.

Where it is now

The operator now runs the test environment. It took over a running Zabbix 7.4.7 installation on the monitoring team's real data, kept their address, certificate and history, and upgraded it to 8.0.0rc1 in about a minute. Then it took over the proxies and agents from a separate Helm release. Every step was backed up first, measured, and written into the documentation and the tests, including the mistakes I found along the way.

That incident could have stayed a bad memory. Instead I paid attention to it, and it became something other people can use.

60 s7.4.7 → 8.0.0rc1 schema upgrade on a 12 GB database, servers stopped for about 35 s
25 sto adopt a running 7.4.7 installation without touching its schema
~7.5 suntil the Service routes to a new active node after a clean failover
55 MB/slz4 base backups to S3, against 2 MB/s with gzip

What it does

Each feature answers something that went wrong, or nearly did.

Routing you can see

The server Service follows the active HA node through a role label. Standbys are Ready and never receive connections, so no setting on the Service has to compensate.

Because session affinity was the wrong fix

Upgrades with guardrails

Patch releases roll one server at a time, standby first. Line upgrades (7.x → 8.0) wait for approval, a recent CNPG backup, healthy replicas and a supported PostgreSQL. A blocked upgrade changes nothing.

Because irreversible steps need a way back

The database first

A thin view of a CloudNativePG cluster decides when Zabbix may connect. During switchovers and PostgreSQL upgrades Zabbix keeps running and reconnects; the operator never writes to CNPG.

Because the data outlives every pod

Pods like CloudNativePG

Stable pod names, one replacement at a time, disruption budgets, no Deployments. Stale ha_node rows are cleaned on a schedule.

Because HA node names should not drift

Suspend on purpose

spec.suspend stops everything in a safe order, frontend first and the active server last, each node marked stopped in Zabbix. Resume brings it back.

Because maintenance should be calm

Proxies and agents

In-cluster proxies and node agents, with optional registration in Zabbix through its API. Only what the operator registered is ever changed.

Because hand-made config must stay untouched

Says what is wrong

Conditions, events and per-component messages name the stuck pod and why: unschedulable, image pull, crash loop. Prometheus metrics, alerts with runbooks and a Grafana dashboard come with it.

Because nobody should have to guess where it came from

Versions as data

Zabbix 7.0, 7.2, 7.4 and 8.0 are built in. New lines can be enabled through a ConfigMap and are flagged as not yet validated, with a full backup required before upgrading.

Because the next release should not wait for the operator

Adopt, don't recreate

Point it at an existing database and it adopts the schema. A migration guide covers moving from plain manifests, Helm, or another operator.

Because real systems already exist

Get started

Requires Kubernetes 1.29+ and CloudNativePG.

VERSION=v0.1.0
kubectl apply -f https://github.com/sagh0900/zabbix-operator/releases/download/$VERSION/install.yaml

# a CNPG cluster and its ZabbixDatabase, then Zabbix itself
kubectl apply -f https://raw.githubusercontent.com/sagh0900/zabbix-operator/main/examples/database.yaml
kubectl apply -f https://raw.githubusercontent.com/sagh0900/zabbix-operator/main/examples/system.yaml
kubectl -n zabbix get zsys -w
